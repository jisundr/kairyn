# Design: Plugin versioning and consumer upgrades

## Approach

Written by hand from playbook 02 (no design stage yet).

Option B, chosen by the user: a manifest, `.kairyn/.base/` copies and a three-way merge. Rejected options:
- (A) Replace unedited files and report every edited file as a conflict. Edited stages would conflict.
- (C) Read stages live from the plugin, with overrides. The repo must own its stages.

All logic goes in one Python module with no dependencies (consumers have plain `python3`). `init.sh` stays the entry point for `/kairyn:init` and calls the module.

## Components

| File | Role |
|---|---|
| `plugin/scripts/kairyn_files.py` | The file table: each installed file, its repo path and its owner (`plugin` or `repo`). Includes `MODEL-ROUTING.md`. Hashing, manifest and `.base/` I/O. |
| `plugin/scripts/upgrade.py` | `/kairyn:upgrade`. Prints one result line per file. |
| `plugin/scripts/version_check.py` | Compares `.kairyn/manifest.json` with `plugin.json`. Silent when they match or `.kairyn/` is absent. |
| `plugin/release-hashes.json` | `{version: {repo path: [sha256]}}`. Generated by `scripts/release_hashes.py` from git history. A version lists hashes from all its commits (0.1.0 changed in #5 to #7). |
| `plugin/commands/upgrade.md` | Runs `upgrade.py`, reports its lines exactly. |
| `plugin/hooks/hooks.json` | `SessionStart` runs `version_check.py --root "$CLAUDE_PROJECT_DIR"`. |
| `.github/workflows/ci.yml` | New job: fails when `plugin/` changes and the `plugin.json` version does not. |

**Manifest** (`.kairyn/manifest.json`): `{"version": "0.2.0", "files": {"<repo path>": {"sha256": "...", "owner": "repo"}}}`. The kairyn `CLAUDE.md` block is entry `CLAUDE.md#kairyn`.

**`.base/`** mirrors repo paths: `.kairyn/.base/.kairyn/stages/REQUIREMENTS.md`. It is committed in the consumer repo.

## Upgrade rules, per file

1. Missing: copy it. `ADDED`.
2. Same as the new file: `KEPT`.
3. Plugin-owned: replace it. `REPLACED`. If the user edited it, save their copy as `<file>.kairyn-old` first.
4. Repo-owned and unedited (matches `.base/` or any hash in `release-hashes.json`): replace it. `REPLACED`.
5. Repo-owned and edited, with a base: `git merge-file -p local base new`. Exit 0: write the result, `MERGED`. Conflict: write the merge to `<file>.kairyn-new`, keep the local file, `CONFLICT`.
6. Edited, no base: `CONFLICT`.

The `CLAUDE.md` block is replaced between its markers, then `harness_docs.py --write` rebuilds the index. The manifest and `.base/` update only for files that did not conflict, so a second run retries the same conflicts and changes nothing else. Exit 1 if any file conflicts. No `git` on the machine: an edited repo-owned file is a `CONFLICT`.

## Bug fixes

- **Budgets**: `budgets.py` adds built-in fallback budgets after the user's patterns: `.kairyn/stages/*.md` 500, `.kairyn/templates/*.md` 200, `.kairyn/learnings.md` 2000, `docs/tasks/*/*.md` 1500. `.kairyn/.base/**` is skipped.
- **Index markers**: `harness_docs.py` refreshes every marker pair in a file, not only the first.
- **`verify-init.sh`**: the default mode checks a repo that is in use: files present, manifest valid, no byte compare of repo-owned files. `--fresh` keeps today's checks for `/kairyn:init` and the init eval.

## Test plan

| Acceptance criterion | Test |
|---|---|
| Manifest and `.base/` after init; init never overwrites | `test_init_manifest.py` |
| Plugin-owned replace; `CLAUDE.md` block only | `test_upgrade.py::plugin_owned` |
| Three-way merge: unchanged, clean, conflict | `test_upgrade.py::merge_*` |
| Adds new files (`MODEL-ROUTING.md`); never touches learnings, tasks, user docs | `test_upgrade.py::scope` |
| Result lines, manifest update, exit code; idempotent | `test_upgrade.py::report`, `::twice` |
| No manifest, release hashes; this repo's stages | `test_upgrade.py::pre_manifest`, fixture `tests/fixtures/consumer-v0.1.0/`; `test_release_hashes.py::all_commits` |
| Version check in check, verify-init, hook | `test_version_check.py` |
| Budgets with a strict `budgets.yml`; index markers | `test_budgets.py`, `test_harness_docs.py` |
| `verify-init.sh` with tasks; v0.1.0 fixture upgrades | `test_verify_init.py`, `test_upgrade.py` |
| Current hashes recorded | `test_release_hashes.py` |
| Version bump in CI | The CI job, shown failing once on a branch |
| Tests first; init eval passes | Review; `uv run python evals/run.py init` |

The CI consumer job also runs `init.sh`, then `upgrade.py`, with plain Python 3.10.

## Standards impact

- **Security**: upgrade writes only inside the repo and never runs repo content.
- **Performance**: the hook is one Python process; a test times it.
- **Portability**: bash and the Python 3.10 standard library; macOS and Linux.
