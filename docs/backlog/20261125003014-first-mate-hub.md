# A first-mate hub that supervises AFK runs

**Raw request:** "I saw this. https://www.claudemod.com/mods/fm And I think this is how we work in cerna-hq" (Jayson De los Reyes, 2026-11-25, Claude Code session)

**Problem (AI draft, needs a human to confirm):** The home agent drives each AFK run by hand. After each `BLOCKED:` it reads the cause, fixes it, sets `status: in-progress` and starts `afk.py` again. One run at a time, and nothing wakes the agent when a run stops or CI finishes.

**Prior art:** FirstMate (`kunchenguid/firstmate`, MIT). The user talks to one "first mate". It starts "crewmates", each in a visible tmux window and its own git worktree. A bash watcher wakes the first mate only when a crewmate needs it. Stop hooks block a turn end without a check. State is on disk, so a restart reconciles.

**Evidence:**
- Task 2026-11-25-skill-names-clash: `afk.py` started four times; each stop needed a manual fix and relaunch. The merge waited on 6 queued CI checks with no wake-up.
- cerna-hq already works this way by hand: a home repo is the remote control, and agent work runs in a server tmux session the user watches.
- Related: `parallel-slices` (parked).
