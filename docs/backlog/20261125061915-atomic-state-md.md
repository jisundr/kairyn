# afk.py writes STATE.md atomically

**Raw request:** "make afk.py's STATE.md write atomic" (Jayson De los Reyes, 2026-11-25, through an Orca coordinator, after PR #35)

**Problem (AI draft, needs a human to confirm):** `Task.update()` (`plugin/scripts/afk.py:318`) writes the task's `STATE.md` with `write_text`, which empties the file first. A reader in that window, or a kill mid-write, sees an empty or partial `STATE.md`. PR #35 fixed the same bug in `milestones.store()` and named this write as the most likely next one.

**Evidence:**
- PR #35: a reader saw `watch.json` empty (macOS CI run 45548893428). Its test made 790 of 3000 reads fail on the old code.
- Readers of the live file in the worktree: a second `afk.py run` or `approve` on the task, `close.py` `task_problem()`, `/kairyn:build` and a first mate checking a run. No reader in the code runs at the same time as `update()`; the risk is another process.
- On an empty read, `front()` returns `None`: `resumable()` says no and a blocked run does not resume. `close.py` reports `has status None, not done`.
- `update()` reads, changes and writes the file. A partial read written back loses front matter and log lines. Git keeps only the last committed copy.
- Other non-atomic writes from PR #35: `afk.py` BUILD.md, GATES.md and REVIEW.md (513, 559, 595, 620, 662, 843), `close.py` (150, 159, 200), `kairyn_files.py:135`, `upgrade.py`, `harness_docs.py`, `budgets_html.py`. One process writes each; nothing polls them.

**Notes:** Inference: copy `store()`'s temp file in the same folder and `os.replace`. Option: one shared atomic-write helper in `plugin/scripts/` that `store()`, `update()` and the writes above all use.
